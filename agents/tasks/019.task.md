# 019 — Configure the Polza.AI API key in Settings

## Objective

Allow the user to add, replace, and remove the Polza.AI API key from the existing **Settings** page. Persist the credential on the backend and use it for all Polza.AI-backed operations, including LLM generation and model-catalog requests. The key must never be returned to or stored by the browser beyond the unsaved password-field value.

## Current state / code to inspect

- The Settings page is `frontend/src/views/settings/SettingsView.tsx` and already contains provider credential controls for Lumean.
- App-wide settings are exposed by `GET/PUT /api/app-settings`; `AppSettingsService` persists them in `<projects>/_app-settings.json` and returns a public settings object that omits the full Lumean key.
- The Polza LLM client (`backend/src/modules/llm/polza-llm.service.ts`) currently reads `POLZA_API_KEY` from `ConfigService` in its constructor, so its credential is fixed at process startup.
- The Polza model catalog (`backend/src/modules/projects/catalog.service.ts`) separately reads `POLZA_API_KEY` from `ConfigService`.
- The frontend settings API, query hook, and shared types are `frontend/src/api/app-settings.api.ts`, `frontend/src/hooks/queries/useAppSettings.hook.ts`, and `frontend/src/types/settings.types.ts`.

Read the current implementations before changing them. Preserve existing Kokoro and Lumean settings, API behavior, and unrelated working-tree changes.

## Implementation requirements

### Backend settings and secret handling

1. Extend the Zod application-settings schema and patch schema with an optional `polzaApiKey`. Accept `null` in a patch to remove the saved key; preserve existing settings when a patch omits this property.
2. Persist the key using the existing app-settings storage path and write mechanism. Keep the full key available only through server-side settings access.
3. Extend the public settings response with a presence flag and masked last-four-character hint (for example, `polzaApiKeySet` and `polzaApiKeyHint`). Never include `polzaApiKey` itself in `GET /api/app-settings`, `PUT /api/app-settings`, logs, or error messages.
4. Retain `POLZA_API_KEY` as an environment-based fallback for existing deployments. Define and implement one consistent precedence rule (prefer an explicitly saved Settings key over the environment fallback). Removing the saved key should restore the documented fallback behavior.
5. Avoid capturing a Settings key at application startup: resolve the effective key when an LLM request or catalog request is made, so saving or replacing it works without restarting the backend. If neither source provides a key, return a clear actionable error instead of crashing startup or making an unauthenticated Polza request.
6. Use the effective key for both `PolzaLlmService` generation (including streaming) and `CatalogService.getModels()`. Keep the existing Polza base URL and AI SDK behavior unchanged.

### Settings page

1. Add an always-visible **Polza.AI** section to the existing Settings page, independent of the selected narration/TTS provider. Include a password input, save/replace action, saved-key hint/status, and remove action when a Settings key is saved.
2. Use the existing app-settings query/mutation and typed API patterns. Clear the input only after a successful save; allow editing unrelated settings without sending or clearing the secret.
3. Clearly explain that the key is stored and used server-side and is never sent back in full. Do not place the credential in browser storage, URLs, client logs, or query keys.
4. Reflect whether a key is available while avoiding ambiguity if an environment fallback is configured. Do not expose the environment key or its contents to the browser.
5. Match the existing Settings form layout and disabled/loading/error behavior.

## Tests and verification

- Backend app-settings tests cover saving, replacing, preserving on partial update, removing the Polza key, correct masked public metadata, and absence of the full secret from public responses.
- LLM tests verify requests use the current saved key, fall back to `POLZA_API_KEY` when no saved key exists, observe replacement/removal without a process restart, and fail clearly without either key. Preserve existing generation, streaming, and reasoning-effort behavior.
- Catalog tests verify the same key precedence and clear missing-key handling for Polza model listing.
- Frontend tests (or the repository's available UI verification approach) cover rendering the Polza section regardless of TTS provider, save/replace/remove mutations, success-only input clearing, and no credential leakage into rendered public settings.
- Run the relevant backend tests, frontend checks, and lint/build commands available in the repository. Report any pre-existing failures separately from regressions.

## Acceptance criteria

- A user can add, replace, and remove a Polza.AI API key from **Settings** without editing `.env` or restarting the backend.
- Script generation/streaming and Polza model-catalog requests use the saved Settings key, with the environment variable as a fallback.
- Public settings responses and frontend state never contain the complete API key; only presence/status and an optional masked hint are returned.
- Existing Lumean key handling, Kokoro device settings, narration-provider selection, and model/voice behavior continue to work.
- Missing credentials result in an actionable error, not an application-startup failure or a silent unauthenticated request.
